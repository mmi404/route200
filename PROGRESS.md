## Decisions log (so a fresh session doesn't re-decide these)

- Map tiles: **OpenFreeMap** (`https://tiles.openfreemap.org/styles/liberty`): free, no API key, no rate limit, acceptable for an overnight unattended build. Swap to MapTiler/Mapbox later if the team wants custom styling and is willing to manage a key.
- Framework: Next.js 15 App Router + TypeScript + Tailwind v4 + MapLibre GL JS directly (no heavy wrapper lib) for control over styling.
- Mock data lives in `lib/data/*.geojson` + `app/api/*` route handlers returning the same shape the real Postgres/Supabase-backed API will return, documented in `docs/WEB_DATA_CONTRACT.md` (written in M7) so Tanim/Faladun know exactly what to implement server-side.
- Deploy target: Vercel (not actually deploying without the user's account; build is verified locally with `npm run build` instead, deploy is a one-click step left for the user).

**Branch**: `ground-view-prototype`, off `3d-terrain-explore` (so it carries phase 2's work without touching it). New route, does not replace `/map/[zoneId]`.

**Decisions**:
- New rendering stack for this feature only: **Three.js via `@react-three/fiber`** (+ `@react-three/drei` for camera/controls helpers). MapLibre (used everywhere else in the app) is a GIS map renderer, not suited to placing/animating individual props (trees, houses, roads) in a walkable scene; this is a deliberate second stack, scoped to this one feature.

Procedurally generated primitive geometry (cones/cylinders for trees, boxes for houses, a simple ribbon for roads, a displaced plane for terrain), not fetched 3D asset models. This avoids any asset-licensing question and keeps the scope buildable, while still giving a game-like feel.
- Data mapping: reuse each zone's real `ChangeEvent` history (no new fabricated fields), bucketed into the existing severity bands to pick a visual state as the slider scrubs: nodata/low -> dense forest scatter; moderate -> patchy clearing; high -> mostly bare ground; severe -> road + a house prop, with the local terrain height reduced in the affected area (the "a hill was here, now it's not" effect). **Walkable rebuild (2026-11-10, branch `ground-view-walkable` off `ground-view-prototype`)**

Decisions (these replace the P1 camera and visual-style decisions above where they conflict):
- **Camera is a first-person walker, not an orbit.** W A S D or arrows to walk, mouse look through pointer lock with drag-to-look as the fallback, Shift to run, Q / E (or [ / ]) to step through time while walking. `OrbitControls` is gone. Pitch is clamped and the eye is always 1.7 m above the ground, so no degenerate view is reachable.

- **Movement is a pure function.** `_lib/player.ts` `stepPlayer(state, input, dt, world)` has no React or three.js in it and is unit tested. `PlayerController.tsx` only feeds it input, ground height at the current severity, and nearby obstacle circles.
- **Scene has its own palette.** `_lib/look.ts` (`LOOK`, `SUN_DIRECTION`) is the single art-direction source for ground, foliage, wood, road, house, sky and light. The scene no longer imports `SEVERITY_FILL` or the UI palette: those are tuned for flat legends, not lit soil.
- **Road is painted on the terrain**, not a separate mesh (the terrain is levelled along a seeded centerline and the ground shader draws packed dirt, wheel tracks and damp edges). This removes the ribbon z-fighting class of bug entirely.
- **Still no assets.** Every tree, plant, stump, house part and pole is a BufferGeometry generated in code with baked vertex color; all ground and sky detail is shader noise.
- **Dev-only QA hook.** In non-production builds `window.__groundDebug` exposes the player's live position, yaw, pitch and ground height so automated checks can assert on real movement. It is never set in production.
